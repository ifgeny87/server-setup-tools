SRV-001 Каркас репозитория и общие параметры Выполнено

каркас логи подключаются следом, SRV-002

Зачем

Скрипты должны лежать по группам и читать один набор параметров SSH, а не зашивать порт и группу в каждый файл.

Что сделать

  1. Завести каталоги 1-server-setup, 2-install-software, 3-user-setup, 4-services, common.
  2. В .gitignore оставить только .idea/.
  3. Корневой .env:
    • SSH_GROUP=ssh
    • USER_GROUPS="sudo ${SSH_GROUP}"
    • SSH_PORT=9999
    • SSH_CONFIG_BACKUP с датой в имени, значение считается при каждом source
  4. Каждый скрипт начинается так: #!/bin/bash, set -euo pipefail, затем . "$(dirname -- "$0")/../common/_misc.sh".

  • Скрипт с loadEnv без .env печатает [ERROR] и выходит с кодом 1.

SRV-002 Единые цветные логи без эмодзи Выполнено

common/_misc.sh после SRV-001 батч в SRV-020 пользуется этим контрактом

Зачем

Пользователь должен по цвету строки понимать, шаг прошёл или нет. Сейчас заготовки уже лежат в common/_misc.sh, но заголовок шага печатает эмодзи, часть скриптов пишет обычным echo, а при set -e заготовленные logerr не достигаются.

Контракт логов

  • loghead — начало шага, без эмодзи. Рамку из # оставить.
  • logok — зелёный [OK].
  • logerr — красный [ERROR], после него скрипт выходит с кодом 1, если работу продолжать нельзя.
  • logwarn — жёлтый [WARN]. Шаг не провален, состояние надо прочитать.
  • logr — текущая операция.
  • logd — серый [DEBUG].
  • Эмодзи убрать и из loghead (сейчас ракета), и из текста Telegram в 40-firewall-monitor.sh.
  • Цвета печатать, когда stdout — терминал. Если stdout не терминал или задан NO_COLOR, печатать те же метки [OK] / [ERROR] / [WARN] без ANSI-кодов, чтобы захваченный лог читался.
  • Вопросы пользователю (read) остаются обычным текстом, без цветовых меток.

Что поменять в скриптах

  1. Каждый скрипт начинает работу с loghead и заканчивает успешный путь через logok. Сейчас без loghead живут 20, 23 по смыслу есть, 40 начинает с logr.
  2. Статусы не писать голым echo. Исключение — приглашение ввода.
  3. Там, где после команды стоит if [ $? -ne 0 ] (скрипты 12 и 13), заменить на if ! команда; then logerr "…"; exit 1; fi. Иначе при set -e свой текст ошибки не печатается, пользователь видит только сырой stderr утилиты.
  4. Команда, которая имеет право не найти совпадение (grep в проверках), не должна краситься как [ERROR]. Для этого её вызывать внутри if.
  5. Батч (SRV-020) не вводит второй формат. Он вызывает те же функции: старт скрипта, [OK] по завершении, [ERROR] с путём скрипта и кодом возврата.

Готово, когда

  • В репозитории нет эмодзи в shell- и python-текстах, которые скрипты показывают или отправляют.
  • Успех любого скрипта виден по зелёному [OK], аварийный выход — по красному [ERROR] и ненулевому коду.
  • Запуск с перенаправлением в файл не оставляет ANSI-кодов.

SRV-006 Ограничить SSH группой и портом из .env Выполнено

1-server-setup/13-ssh-restrict.sh после SRV-005 запуск от root

Зачем

Root по SSH закрыт, вход только у группы SSH_GROUP, порт берётся из SSH_PORT, а не остаётся 22.

Что сделать

  1. Файл 1-server-setup/13-ssh-restrict.sh. checkRoot, loadEnv. Нет SSH_GROUP, SSH_PORT или SSH_CONFIG_BACKUP — [ERROR].
  2. Создать группу SSH_GROUP, если её ещё нет.
  3. Скопировать /etc/ssh/sshd_config в SSH_CONFIG_BACKUP. Сбой копирования — [ERROR] через if !. Путь бэкапа записать через logd.
  4. sed удаляет из конфига строки PermitRootLogin, PasswordAuthentication, PubkeyAuthentication, AuthenticationMethods, AllowGroups, Port.
  5. Дописать блок: PermitRootLogin no, PasswordAuthentication yes, PubkeyAuthentication yes, AuthenticationMethods publickey,password, AllowGroups из SSH_GROUP, Port из SSH_PORT. В комментарии блока — пользователь и timestamp.

  7. Затем sshd -t. Сбой — [ERROR] и выход. Строку permitrootlogin из sshd -T прочитать внутри if, чтобы пустой grep не был [ERROR].
  8. logok печатает порт, прочитанную строку, требование ключа и пароля, путь бэкапа.

Сейчас restart идёт раньше sshd -t, поэтому битый конфиг успевает перезапустить сервис. Порядок проверки — SRV-018. Повторный запуск каждый раз рестартует ssh — SRV-019.

Готово, когда

  • В sshd_config есть порт из .env, AllowGroups равен SSH_GROUP, root по SSH запрещён.
  • Рядом с конфигом лежит файл бэкапа из SSH_CONFIG_BACKUP.
  • Успешный прогон заканчивается [OK].

SRV-008 Закрыть вход iptables и сохранить правила Выполнено

1-server-setup/15-secure-firewall.sh после SRV-007 ufw не используется

Зачем

Снаружи остаются SSH на порту из .env, HTTP и HTTPS. Остальной вход отбрасывается и пишется в лог, чтобы его мог читать монитор из SRV-015.

Что сделать

  1. Файл 1-server-setup/15-secure-firewall.sh. loadEnv. Нет SSH_PORT — [ERROR]. checkRoot нет.
  2. Создать цепочку DOCKER-USER, если её нет, затем очистить. В неё добавить accept для RELATED,ESTABLISHED.
  3. Очистить INPUT и собрать заново: lo, established, tcp SSH_PORT, tcp 80, tcp 443, входящие udp/tcp с source-port 53.
  4. В OUTPUT добавить udp/tcp на dport 53.
  5. Перед отбрасыванием: INPUT с лимитом 5/min, префикс лога FIREWALL DROP:, затем INPUT DROP.
  6. В FORWARD вставить accept для интерфейса docker0 в обе стороны.
  7. Поставить iptables-persistent, каталог /etc/iptables, сохранить через netfilter-persistent save или iptables-save в /etc/iptables/rules.v4.
  8. Юнит /etc/systemd/system/secure-firewall.service: Type=oneshot, ExecStart и ExecReload — iptables-restore /etc/iptables/rules.v4, WantedBy=multi-user.target. daemon-reload, enable, start.
  9. logok.

Очистка INPUT снимает правила fail2ban, а правила docker0 падают, если интерфейса нет. Повтор дописывает DNS в OUTPUT и accept в FORWARD. Это SRV-018 и SRV-019.

Готово, когда

  • В INPUT есть accept на SSH_PORT, 80 и 443, затем лог FIREWALL DROP: и DROP.
  • Файл /etc/iptables/rules.v4 создан, юнит secure-firewall.service включён.
  • Скрипт заканчивается [OK].

SRV-019 Повторный запуск без поломки системы Выполнено

идемпотентность опирается на логи из SRV-002

Зачем

Если скрипт оборвался на середине, пользователь запускает его ещё раз. Второй прогон должен доделать недостающее и не дублировать правила, строки конфигов и пользователей.

Колонка «Что сделать» перенесена в скрипты. Два полных прогона подряд на Ubuntu 22.04 и 24.04 отсюда не запускались: нет ВМ. Повтор блоков, конфига SSH и набора iptables проверен локально на примерах файлов.

Общие приёмы

  • Пакет: dpkg -s успешен — не ставить заново, писать [OK] «уже установлен».
  • Конфиг, которым владеет скрипт: блок между метками # BEGIN sst <имя> и # END sst <имя>. Повтор заменяет только блок. Содержимое совпало — файл не трогать и сервис не перезапускать.
  • Пользователь, группа, юнит systemd, строка в authorized_keys: проверить getent / systemctl is-enabled / точное вхождение строки. Создавать только отсутствующее.
  • Обрыв на середине лечится тем же прогоном: уже сделанные шаги пропускаются, первый несделанный выполняется.
  • Неотменяемое действие, которое рвёт сессию (смена порта SSH), перед выполнением писать [WARN]. Это не повод отказываться от повтора.

SRV-020 Батч-скрипт: выбор, вопросы, стоп на ошибке Выполнено

batch/run.sh логи: SRV-002 формат пресетов: SRV-021

Меню, вопросы и остановка очереди проверены локально. Полный sudo ./batch/run.sh на Ubuntu не запускался. Пресет default уже в репозитории. Пресеты без вопросов — SRV-021.

Зачем

Сейчас пользователь сам помнит порядок из 15 файлов. Нужна одна команда: она показывает набор, забирает все ответы до старта и гоняет скрипты по очереди. Первая ошибка останавливает очередь и остаётся на экране.

Точка входа

batch/run.sh. Рядом каталог batch/presets/. Скрипт подключает common/_misc.sh. Корневой .env читает по пути от своего файла (batch/../.env), не через нынешний loadEnv: тот считает, что скрипт лежит на один уровень ниже корня, для batch/run.sh это случайно совпадёт, для запуска из другого места — нет. Дочерние скрипты по-прежнему читают .env сами.

Запуск от root, потому что почти вся цепочка вызывает checkRoot. Шаги 20 и 30 батч запускает через sudo -u "$TARGET_USER" -H, сам батч при этом root.

Порядок фаз

  1. Выбрать пресет. Без аргументов — пресет default (его состав задаёт SRV-021).
  2. Показать список шагов этого пресета. Отмеченные выполняются. Пользователь подтверждает набор или меняет его до любых установок пакетов.
  3. Собрать данные, которые нужны отмеченным шагам. Спросить каждый пункт один раз. Если переменная уже есть в окружении — не спрашивать.
  4. Выполнить отмеченные скрипты по порядку пресета. Цвета только из _misc.sh.
  5. Ненулевой код дочернего скрипта: [ERROR] с путём скрипта и кодом, выход с тем же кодом. Следующие шаги не запускать.

Как выбирается набор

Печатать номера и метки [x] / [ ]. Пустая строка — начать прогон отмеченных. Номер и Enter — переключить пункт. Строка preset <id> — подменить набор другим пресетом и снова показать список. q — выход без изменений в системе.

Это строковый ввод, не меню стрелками: шагов больше девяти, одной цифры не хватает. Меню стрелками относится только к форварду (SRV-023).

Пресет: default
  [x] 1  1-server-setup/10-prepare-tools.sh
  [x] 2  1-server-setup/11-remove-mail-server.sh
  [x] 3  1-server-setup/12-add-user.sh
  [ ] 4  2-install-software/21-install-node.sh
Enter — выполнить отмеченные, номер — переключить, preset <id> — сменить пресет, q — выход

Неинтерактивный запуск

Флаги закладываются здесь, файлы пресетов — в SRV-021.

  • --preset <id> — какой файл из batch/presets.
  • --yes — не спрашивать состав. Вместе с пресетом, у которого INTERACTIVE=no, не спрашивать и значения.

  • Повторный запуск батча после SRV-019 доходит до конца на уже настроенной машине.
SRV-021 Пресеты для запуска без участия пользователя Выполнено

batch/presets исполнитель: SRV-020

Зачем

Авторазвёртывание не может отвечать на вопросы. Пресет — это инструкция батчу: какие скрипты, в каком порядке, какие переменные обязательны, можно ли спрашивать человека.

Пресеты unattended-server и unattended-web добавлены. Список, отказ без NEW_USER_LOGIN и очередь без вопросов проверены локально. Полный прогон apt на Ubuntu не запускался.

Формат

Один пресет — один файл batch/presets/<id>.conf. Парсер на bash, без yq и python. Поля:

  • ID — совпадает с именем файла.
  • TITLE — строка для списка --list.
  • INTERACTIVE=prompt или INTERACTIVE=no.
  • STEP <путь от корня репозитория> — по порядку. Необязательный суффикс user означает запуск от TARGET_USER.
  • NEED <ПЕРЕМЕННАЯ> — относится к предыдущему STEP. Необязательный prompt="текст" — вопрос в режиме prompt. В режиме no текст не используется: переменная должна быть уже экспортирована.

Секреты в файл пресета в репозитории не писать. NEW_USER_SSH_KEY приходит из окружения процесса. Локальные значения, если их неудобно экспортировать руками, класть в batch/presets/*.local и добавить маску в .gitignore. В git остаются только инструкции без ключей.

SRV-023-3. Добавление

Спросить по порядку, пустое значение не принимать, порт вне 1–65535 и не-IPv4 спрашивать заново:

  1. LOCAL_SSH_PORT — локальный tcp, который слушает этот шлюз
  2. LOCAL_AWG_PORT — локальный udp
  3. LOCAL_IP — адрес этого шлюза, подставляется в SNAT
  4. SERVER_SSH_PORT — tcp на удалённой машине
  5. SERVER_AWG_PORT — udp на удалённой машине
  6. SERVER_IP — куда уходит DNAT

LOCAL_IP и SERVER_IP не должны совпадать. Одинаковая шестёрка в конфиге — [ERROR], iptables не менять.

Исходные команды оставляют ту же схему: PREROUTING DNAT, POSTROUTING SNAT, FORWARD ACCEPT, отдельно tcp для SSH и udp для AWG. Меняется способ применения, чтобы повтор и второе такое же правило не копили копии.

  • У каждого правила комментарий -m comment --comment: sst-fwd-<id>-ssh-dnat, sst-fwd-<id>-ssh-snat, sst-fwd-<id>-ssh-fwd и те же три с awg.
  • В FORWARD добавлен -d SERVER_IP. Без него правило принимает любой трафик на этот порт назначения, и по одному порту его нельзя отличить от чужого правила при удалении. DNAT и SNAT остаются на тех же цепочках и адресах, что в исходных командах.
  • Перед добавлением смотреть iptables -S и iptables -t nat -S. Если строка с теми же цепочкой, протоколом, портами и адресами уже есть — не добавлять, даже если у старой строки нет комментария. Если строки нет — добавить каноническую с комментарием.
  • id — следующее целое, не переиспользовать удалённые.

Канонические команды, по одной на SSH и те же с udp и портами AWG:

iptables -t nat -A PREROUTING -p tcp --dport "$LOCAL_SSH_PORT" \
  -m comment --comment "sst-fwd-$id-ssh-dnat" \
  -j DNAT --to-destination "$SERVER_IP:$SERVER_SSH_PORT"

iptables -t nat -A POSTROUTING -p tcp -d "$SERVER_IP" --dport "$SERVER_SSH_PORT" \
  -m comment --comment "sst-fwd-$id-ssh-snat" \
  -j SNAT --to-source "$LOCAL_IP"

iptables -A FORWARD -p tcp -d "$SERVER_IP" --dport "$SERVER_SSH_PORT" \
  -m comment --comment "sst-fwd-$id-ssh-fwd" \
  -j ACCEPT

Конфиг дописывается только после того, как все шесть правил либо уже были, либо успешно добавлены. Иначе в конфиге не появится запись, под которую в iptables легла только часть. Формат, по одной записи на строку:

# id local_ssh_port local_awg_port local_ip server_ssh_port server_awg_port server_ip
1 2222 51821 10.0.0.1 22 51820 203.0.113.10

Добавление пишет живой iptables и конфиг. Файл rules.v4 оно не обновляет: пока пользователь не выберет «Сохранить», список должен показать, что после ребута правила не поднимутся.

SRV-023-4. Удаление

  1. Показать записи конфига номерами. Конфиг пуст — [WARN] и возврат в меню.
  2. Пользователь вводит номер. Чужой номер — спросить снова. Подтверждение словом yes.
  3. Снять все шесть правил этой записи, включая старые копии без комментария. Удалять в цикле, пока iptables -S ещё содержит строку с этими адресами и портами в соответствующей цепочке. Порядок снятия: FORWARD, POSTROUTING, PREROUTING.
  4. Вычеркнуть строку из конфига и переписать файл. id других записей не менять.
  5. rules.v4 не трогать. После удаления список показывает расхождение: в конфиге и в живом iptables правила нет, в снимке оно ещё есть, пока не сделают «Сохранить».

SRV-023-5. Список

Строка на каждую запись конфига. Дополнительно строки, у которых в живом iptables или в rules.v4 есть комментарий sst-fwd-, а в конфиге такого id нет: это «только в iptables» или «только в снимке».

Для записи проверяются все 6 правил. Статус живого iptables и статус rules.v4 считаются отдельно:

  • [OK] полное — найдены все 6;
  • [WARN] неполное — найдена часть;
  • [ERROR] нет — не найдено ни одного.

Колонка «после перезагрузки»:

  • [OK] сохранится — в rules.v4 полное и в sysctl-файле включён ip_forward;
  • [WARN] пропадёт — в живом iptables правила есть, в rules.v4 полного набора нет;
  • [WARN] не в iptables — запись есть в конфиге, в живом наборе её нет;
  • [ERROR] не поднимется — в снимке правила есть, но ip_forward после загрузки будет выключен.

Пример, ширину колонок держать через printf:

id  куда на этом шлюзе              куда на сервере                 конфиг  iptables   rules.v4   после ребута
1   10.0.0.1 tcp/2222 udp/51821      203.0.113.10 tcp/22 udp/51820   да      [OK]       [ERROR]    [WARN] пропадёт

Под таблицей одной строкой повторить пути конфига и rules.v4, чтобы было понятно, какой файл переживёт ребут, а какой только помнит намерение скрипта.

SRV-023-6. Сохранить

Спросить yes. Пояснить, что в /etc/iptables/rules.v4 попадёт весь текущий iptables, включая правила скрипта 15, не только форвард. Затем iptables-save в этот файл. Если есть netfilter-persistent, дополнительно netfilter-persistent save. Успех — [OK] с путём. Этот шаг и есть «правила, которые будут после перезагрузки», если юнит из скрипта 15 или пакет iptables-persistent восстанавливает rules.v4.

SRV-023-7. Загрузить

Это замена текущего iptables содержимым снимка, не слияние. Если файла нет — [ERROR] и возврат в меню. Перед iptables-restore спросить yes и напечатать [WARN]: пропадут несохранённые правила, SSH может оборваться, если в снимке другой порт или нет accept для текущего порта. Команда: iptables-restore < /etc/iptables/rules.v4. Конфиг форварда при загрузке не менять: он хранит намерение, а снимок хранит то, что реально залито в iptables. Расхождение после загрузки видно в списке.

Готово, когда

  • При старте напечатаны оба пути.
  • Пункты выбираются стрелкой и Enter и отдельно цифрой 1–5 без Enter.
  • Два добавления одной и той же шестёрки не увеличивают iptables -S и iptables -t nat -S. Второе добавление заканчивается [ERROR] и не пишет вторую строку конфига.
  • После добавления без сохранения список показывает полное в iptables и «пропадёт» для ребута. После «Сохранить» — «сохранится», если ip_forward включён.
  • Удаление снимает правила, убирает строку конфига и не оставляет копий. Снимок меняется только отдельным сохранением.
  • Загрузка подменяет текущие правила файлом. Отказ ответить yes не вызывает iptables-restore.
SRV-024 Кастомные страницы ошибок nginx Выполнено

Зачем

Сейчас nginx отдаёт свою стандартную страницу. Нужен один общий экран на коды ошибок: короткий, в терминальном стиле, и он сам подстраивается под светлую или тёмную тему системы. Картинок и анимации нет.

  4. Значения печатает nginx SSI, не JS. JS только копирует код из заголовка в document.title. На странице четыре поля: код ответа ($status), версия (nginx/$nginx_version), адрес ($scheme://$host$request_uri), время запроса ($time_iso8601).

Клиенту остаётся исходный код, не 200: если голый error_page подменяет его, писать error_page 404 =404 @sst_error и так для каждого кода. Если SSI видит $status как 200, передать в страницу настоящий код, не копируя HTML тринадцать раз.
  6. В каждый server в /etc/nginx/conf.d/*.conf и sites-enabled вставить include /etc/nginx/snippets/sst-errors.conf;, если этой строки в блоке ещё нет. Второй запуск строку не дублирует.
  7. Ту же строку include добавить в шаблоны, из которых заново пишутся конфиги: оба server в 2-install-software/24-install-nginx-certbot.sh и server в 4-services/41-add-ssl-certificate.sh. Иначе повтор 24 или 41 сотрёт подключение страницы.
  8. Перед перезагрузкой nginx -t. Тест не прошёл — не делать reload, [ERROR] и выход. Прошёл — nginx -s reload и [OK] с путём HTML.

Готово, когда

  • Запрос несуществующего пути возвращает тот же код в статусе ответа и в теле страницы. В теле есть nginx/ с версией, запрошенный URL и время в формате ISO.
  • В error.html нет ссылок на картинки и нет правил анимации. Светлая и тёмная тема системы дают разные цвета текста и фона.
  • Новый конфиг из скрипта 41 уже содержит include сниппета.
Штатные ответы и чужой error_page — SRV-025. Снятие страниц — SRV-026.
SRV-025 Страницы ошибок не ломают штатный nginx Можно делать

nginx правка 4-services/43-nginx-error-pages.sh, 2-install-software/24-install-nginx-certbot.sh, 4-services/41-add-ssl-certificate.sh после SRV-024

Зачем

Скрипт 43 подменяет только тело выбранных кодов ошибок. Остальная работа nginx должна остаться той же, что до запуска: живые сайты, редиректы, сертификат, чужая страница ошибок в конкретном server. Сейчас это не закреплено, и неудачный nginx -t оставляет уже переписанные конфиги.

Что сейчас расходится со штатной работой

  • Include вставляется в каждый server в /etc/nginx/conf.d/*.conf и sites-enabled, даже если в этом блоке уже есть свой error_page. Строка стоит сразу после server {, поэтому более поздняя директива сайта пока побеждает. Перенос строки в конец блока перебьёт чужую страницу.
  • Сниппет и include пишутся до nginx -t. Тест не прошёл — reload нет, но файлы уже другие.
  • Скрипты 24 и 41 сами создают пустой /etc/nginx/snippets/sst-errors.conf и вшивают include в шаблон. Пока 43 не запускали, тела ответов штатные, но в конфиге уже чужая строка. Установка nginx без скрипта 43 не должна знать про sst-errors.
  • Нет проверки, что ответ вне списка кодов не стал страницей error.html и что код ошибки не сменился на 200.

Что сделать

  1. Убрать include /etc/nginx/snippets/sst-errors.conf; и создание пустого сниппета из 24-install-nginx-certbot.sh и 41-add-ssl-certificate.sh. Эти скрипты снова пишут только свой сервер. Файл сниппета и строку include создаёт только 43.
  2. В 43 перед правкой сохранить копию каждого конфига, который скрипт собирается менять, и копию сниппета, если он уже был. Каталог копий — временный, после успеха удалить.
  3. Include добавлять прежним правилом: один раз, сразу после открывающей строки server {, только в /etc/nginx/conf.d/*.conf и sites-enabled. Если в этом блоке уже есть директива error_page, блок не трогать и написать [WARN] с путём файла. Не переносить include в конец блока.
  4. Сниппет по-прежнему только про коды из SRV-024 и location @sst_error. Не добавлять recursive_error_pages, не ставить ssi вне этого location, не менять root, listen, server_name, ssl_certificate сервера. Коды 200, 204, 301, 302 не перехватывать. return 404 у default-сервера скрипта 24 остаётся кодом 404, меняется только тело.
  5. nginx -t не прошёл — вернуть копии конфигов и прежний сниппет, не делать reload, [ERROR] и выход. Прошёл — reload и [OK].
  6. Повторный запуск по-прежнему не дублирует include.

Готово, когда

  • После скриптов 24 и 41, без 43, в конфигах нет sst-errors, файла сниппета нет, nginx -t проходит, страница ошибки — штатная nginx.
  • server со своим error_page после 43 не изменён. server без своего error_page получает одну строку include.
  • Запрос существующего ресурса сохраняет прежний код и не отдаёт error.html. Запрос отсутствующего пути сохраняет код ошибки, не 200, и отдаёт error.html. Прямой запрос к @sst_error снаружи не обслуживается.
  • Если в конфиг заранее положена синтаксическая ошибка, 43 возвращает файлы как было и не вызывает reload.
