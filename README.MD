# Server Setup Tools

* Repo: https://github.com/ifgeny87/server-setup-tools
* Version: 1.0.0

Скрипты первичной настройки VPS на Ubuntu 22 и 24: безопасный SSH, ограничение портов через iptables, установка типового ПО. ufw этот набор не ставит и не настраивает.

## Клонирование

```shell
apt-get update -y; apt-get install -y git
cd /opt
git clone https://github.com/ifgeny87/server-setup-tools
cd server-setup-tools
```

Локально можно смотреть файлы в контейнере Ubuntu. Это не замена прогона на ВМ: в контейнере нет полноценного sshd и systemd.

```shell
docker run -it --rm -v "$PWD":/opt/server-setup-tools ubuntu /bin/bash
```

## Каталоги

- `1-server-setup` — подготовка сервера. Запуск от root.
- `2-install-software` — пакеты. От root, кроме `20-install-oh-my-zsh.sh`: его запускает сам пользователь.
- `3-user-setup` — конфиги домашнего каталога. Запуск от пользователя, не от root.
- `4-services` — nginx, монитор, форвард. От root.
- `batch` — очередь скриптов по пресету.
- `common` — общие функции, сам по себе не запускается.

Повторный запуск смотрит текущее состояние: уже созданный пользователь не падает, совпавший конфиг не переписывается и не перезапускает сервис. Исключение — `10-prepare-tools.sh`: `apt-get upgrade` выполняется каждый раз.

## Как не потерять SSH

Скрипт 13 включает вход только по публичному ключу и паролю вместе, запрещает root и меняет порт. Скрипт 15 после этого закрывает все входящие порты, кроме нового SSH, 80 и 443.

Перед прогоном, если SSH — единственный вход:

1. В корневом `.env` выставить `SSH_PORT` заранее. Значение по умолчанию в репозитории — `9999`.
2. Иметь второй канал: консоль провайдера или уже открытая сессия, которую не жалко оборвать.
3. Скриптом 12 создать пользователя и положить публичный ключ. Сразу задать ему пароль: `passwd ИМЯ`. Без пароля после скрипта 13 войти нельзя: нужны и ключ, и пароль.
4. После скрипта 13 текущая сессия на старом порту оборвётся. С другой машины открыть новую сессию на `SSH_PORT` этим пользователем и убедиться, что она жива.
5. Только потом запускать скрипт 15. После него старый порт файрволом уже закрыт. Если новая сессия не открылась, без консоли на сервер не зайти.

Батч `unattended-server` и `unattended-web` сам проходит 13, затем 14 и 15. Перед шагом 13 он печатает предупреждение и не ждёт. Для машины только с SSH этого мало: порт в `.env` и второй канал нужны до старта батча.

## Переменные `.env`

Файл лежит в корне репозитория. Его читает `loadEnv` из `common/_misc.sh`: путь считается от каталога скрипта на уровень вверх, то есть для скриптов из `1-server-setup` это корневой `.env`. Батч читает тот же файл напрямую.

| Переменная | Зачем |
| --- | --- |
| `SSH_GROUP` | Группа, которой разрешён SSH. В файле из репозитория: `ssh`. |
| `USER_GROUPS` | Группы нового пользователя через пробел. В файле: `sudo` и значение `SSH_GROUP`. |
| `SSH_PORT` | Порт sshd и единственный входящий SSH-порт в iptables. В файле: `9999`. |
| `SSH_CONFIG_BACKUP` | Куда скрипт 13 копирует `sshd_config`, если файл реально меняется. |

`SSH_CONFIG_BACKUP` в `.env` записан так:

```shell
SSH_CONFIG_BACKUP="/etc/ssh/sshd_config.backup_$(date +%Y%m%d_%H%M%S)"
```

Команда `date` выполняется при каждом `source` этого файла, не один раз при создании. Повторный запуск скрипта 13, если конфиг снова изменился, пишет новый бэкап с новым временем.

Остальные переменные в `.env` не лежат. Их задают в окружении или отвечает терминал:

- `NEW_USER_LOGIN`, `NEW_USER_SSH_KEY` — скрипт 12.
- `CERTBOT_EMAIL` — скрипт 24, только если аккаунта certbot ещё нет.
- `DOMAIN` — скрипт 41.
- `FORCE_NGINX=1` — скрипт 41, заменить уже существующий конфиг домена.
- `VERSION` — скрипт 21, мажор Node.js. Пустое значение значит 25.
- `TELEGRAM_API_TOKEN`, `TELEGRAM_CHAT_ID` — скрипт 40, файл `/root/.env` или окружение.
- `TARGET_USER` — батч, от чьего имени запускать скрипты 20 и 30.

Секреты для батча кладут в `batch/presets/<id>.local`. Файлы `batch/presets/*.local` в git не входят.

## `common/_misc.sh`

Подключается скриптами, отдельно не запускается.

- Логи: `[OK]`, `[ERROR]`, `[WARN]`, обычная строка и отладочная. Цвет есть только если stdout — терминал и не задан `NO_COLOR`.
- `checkRoot` завершает скрипт, если UID не 0.
- `loadEnv` читает `.env` на уровень выше каталога скрипта.
- `sst_write_if_changed` пишет файл, только если байты изменились, и ставит `SST_FILE_CHANGED`.
- `sst_replace_block` заменяет текст между `# BEGIN sst ИМЯ` и `# END sst ИМЯ`, строки вне блока оставляет.

## `batch/run.sh`

Единая точка входа в очередь. Запуск от root: почти все шаги сами вызывают `checkRoot`. Скрипты 20 и 30 батч запускает через `sudo -u "$TARGET_USER" -H`, даже если в пресете нет суффикса `user`.

```shell
sudo ./batch/run.sh --list
sudo ./batch/run.sh
sudo ./batch/run.sh --preset unattended-server --yes
```

`--list` не требует root и печатает пресеты: `default`, `unattended-server`, `unattended-web`.

Без флага `--preset` берётся `default`: шаги 10–15, вопросы логина и ключа. Пустая строка в меню запускает отмеченные пункты. Номер переключает пункт. `preset <id>` меняет набор. `q` выходит, ничего не ставя.

`--yes` пропускает это меню. Без терминала нужны оба флага, `--preset` и `--yes`, иначе `[ERROR]` до любого скрипта.

Пресет `unattended-server` (`INTERACTIVE=no`) — те же шаги 10–15 без вопросов. Логин и ключ должны уже быть в окружении, иначе батч печатает `[ERROR] Нет переменной …` и выходит до проверки root и до скрипта 10:

```shell
sudo NEW_USER_LOGIN=user1 \
  NEW_USER_SSH_KEY='ssh-ed25519 AAAA... user@computer' \
  ./batch/run.sh --preset unattended-server --yes
```

Пресет `unattended-web` добавляет Docker, автоочистку образов, nginx с certbot, сертификат домена и страницы ошибок. Дополнительно нужны `CERTBOT_EMAIL` и `DOMAIN`. Скриптов 20, 21, 30, 40, 42 и 44 в этом пресете нет.

Ненулевой код дочернего скрипта останавливает очередь: `[ERROR] Остановлено на <путь>, код N`, следующие шаги не запускаются. Перед `13-ssh-restrict.sh` батч печатает `[WARN]`: сейчас сменится порт SSH из `.env`, текущая сессия оборвётся. Это не вопрос.

## 1. Подготовка сервера

Порядок: 10, 11, 12, 13, 14, 15, затем перезагрузка. Все шесть запускаются от root.

Скрипт 14 ставит fail2ban на порт из `SSH_PORT`. Скрипт 15 заново собирает цепочку INPUT с политикой DROP и сохраняет уже висящие переходы `-j f2b-`. Если после применения таких переходов нет, а fail2ban установлен, скрипт 15 перезапускает fail2ban, чтобы тот вернул свои цепочки. Поэтому 14 идёт раньше 15.

### `1-server-setup/10-prepare-tools.sh`

Ставит базовые пакеты и обновляет систему. Запуск от root. Переменные не читает.

1. `DEBIAN_FRONTEND=noninteractive`, чтобы вопросы apt не останавливали скрипт.
2. `apt-get update`.
3. `apt-get upgrade` с `--force-confdef` и `--force-confold`: существующие конфиги пакетов не спрашиваются и не затираются новой версией.
4. Устанавливает `zsh tmux vim mc htop git gh net-tools`.

Повтор снова делает update и upgrade. Это ожидаемо.

```shell
sudo ./1-server-setup/10-prepare-tools.sh
```

### `1-server-setup/11-remove-mail-server.sh`

Убирает предустановленную почту, чтобы она не слушала 25/587/465. Запуск от root. `.env` не читает.

Пакеты: `postfix`, `exim4`, `sendmail`, `mailutils`, `cyrus-imap`, `dovecot`. Для установленного пакета сначала останавливается и отключается его юнит (`postfix`, `exim4`, `sendmail`, `dovecot`, для `cyrus-imap` — `cyrus-imapd`). У `mailutils` юнита нет. Затем `apt-get purge`. Неустановленный пакет пропускается.

Дальше удаляются каталоги `/etc/postfix`, `/etc/exim4`, `/etc/sendmail*`, `/var/log/exim4`, `/var/log/mail*`, очереди `/var/spool/postfix/*` и `/var/spool/exim4/*`, затем `autoremove` и `apt-get clean`.

Повтор снова проходит список. Уже снятые пакеты не ошибка. Каталоги почты удаляются и во второй раз.

```shell
sudo ./1-server-setup/11-remove-mail-server.sh
```

### `1-server-setup/12-add-user.sh`

Создаёт пользователя без пароля и дописывает ему публичный ключ. Запуск от root. Пароль здесь не задаётся: после скрипта нужен `passwd`. Запрет root и смена порта — это скрипт 13, не этот.

Читает из `.env`: `SSH_GROUP`, `USER_GROUPS`. Из окружения или с терминала: `NEW_USER_LOGIN`, `NEW_USER_SSH_KEY`. Ключ — одна строка вида `ssh-ed25519 AAAA... комментарий` или `ssh-rsa ...`. Это публичный ключ, не сертификат.

1. Если группы `SSH_GROUP` нет, создаёт её.
2. Если пользователя нет, `adduser --disabled-password`. Если есть, не падает и идёт дальше.
3. Добавляет недостающие группы из `USER_GROUPS`. Группы `sudo` на системе нет — ошибка, сначала нужен скрипт 10. Другую отсутствующую группу создаёт.
4. Ключ дописывается в `~/.ssh/authorized_keys`, файл не обрезается. Та же строка второй раз не пишется. Права: каталог `700`, файл `600`, владелец — пользователь.
5. Пустой ключ и уже непустой `authorized_keys` — пропуск ключа. Пустой ключ и пустой файл — ошибка. Спросить ключ скрипт может только в терминале.

```shell
sudo NEW_USER_LOGIN=user1 \
  NEW_USER_SSH_KEY='ssh-ed25519 AAAA... user@computer' \
  ./1-server-setup/12-add-user.sh
sudo passwd user1
```

### `1-server-setup/13-ssh-restrict.sh`

Ограничивает sshd. Запуск от root. Читает `SSH_GROUP`, `SSH_PORT`, `SSH_CONFIG_BACKUP`. Раньше него должен быть скрипт 12: пользователь в группе `SSH_GROUP`, ключ на месте, пароль задан.

В конец `/etc/ssh/sshd_config` пишется один блок `# BEGIN sst ssh-restrict`:

- `PermitRootLogin no`
- `PasswordAuthentication yes`
- `PubkeyAuthentication yes`
- `AuthenticationMethods publickey,password` — нужны оба фактора, ключ и пароль
- `AllowGroups` из `SSH_GROUP`
- `Port` из `SSH_PORT`

Такие же директивы вне блока и старый комментарий `# --- Restrict SSH Access ---` снимаются, чтобы при повторе не копиться.

Если текст файла изменился, сначала копия в `SSH_CONFIG_BACKUP`, затем `sshd -t`. Проверка не прошла — файл возвращается из копии, ssh не перезапускается. Проверка прошла — `systemctl restart ssh` (или `sshd`, если юнит называется так).

В момент перезапуска текущая сессия на старом порту оборвётся. Новую сессию на `SSH_PORT` нужно открыть и проверить до скрипта 15: после файрвола старый порт уже закрыт.

Повтор при совпавшем файле и уже слушающем порте ssh не трогает и бэкап не пишет. Если `sshd -T` показывает другой порт или порт ещё не слушается, будет предупреждение и перезапуск.

```shell
sudo ./1-server-setup/13-ssh-restrict.sh
```

### `1-server-setup/14-install-fail2ban.sh`

Ставит fail2ban на SSH-порт из `.env`, не на 22. Запуск от root после скрипта 13. Читает `SSH_PORT`.

Пакет ставится, только если его ещё нет. Файл `/etc/fail2ban/jail.local`: бан через `iptables-multiport`, jail `sshd`, `maxretry = 3`, `findtime = 600`, `bantime = 604800` (7 дней), лог `/var/log/auth.log`, `port` равен `SSH_PORT`. Почта и sendmail в jail не настраиваются.

Совпавший `jail.local` не переписывается. Сервис перезапускается, только если файл изменился или он не активен. Иначе он просто включён в автозапуск.

```shell
sudo ./1-server-setup/14-install-fail2ban.sh
```

### `1-server-setup/15-secure-firewall.sh`

Закрывает вход через iptables и, если ядро не выключило IPv6, через ip6tables. Запуск от root после 13 и 14. Читает `SSH_PORT`. ufw не используется. Форвард включается только вместе с DROP на FORWARD: это делает скрипт 15, скрипт 42 сам пересылку не открывает, пока политики DROP нет.

Ставит `iptables-persistent`, если пакета нет. Таблицу filter собирает заново и подменяет целиком, без вторых копий правил:

- политики INPUT и FORWARD — DROP;
- вход: `lo`, уже установленные соединения, tcp `SSH_PORT`, tcp 80, tcp 443;
- пакет с source-port 53 во вход не принимается, ответ DNS проходит как established;
- перед DROP — лог `FIREWALL DROP:` не чаще 5 в минуту, burst 5;
- исходящий DNS: udp и tcp на порт 53;
- переходы INPUT на цепочки fail2ban (`-j f2b-`) сохраняются;
- правила `sst-fwd-` в FORWARD сохраняются;
- если интерфейса `docker0` нет, правила Docker пропускаются с `[WARN]`;
- если `docker0` есть: FORWARD с него и на него, плюс RELATED,ESTABLISHED в `DOCKER-USER`.

IPv6 в ядре выключен — одна строка в лог, IPv4 всё равно настраивается, код выхода 0. IPv6 включён, а `ip6tables` нет — ошибка до подмены правил. Иначе ip6tables получает тот же вход, ошибки ICMPv6 (типы 1–4) и neighbor discovery (типы 133–136). Echo request и source-port 53 в IPv6 не открываются.

Фраза «только SSH и HTTPS» была бы неточной: открыты также 80 и исходящий DNS.

Дальше скрипт сохраняет весь текущий iptables в `/etc/iptables/rules.v4` (через `netfilter-persistent save`, если команда есть). При включённом IPv6 рядом пишется `/etc/iptables/rules.v6`. Юнит `secure-firewall.service` при загрузке восстанавливает `rules.v4`, а если IPv6 включён — ещё и `rules.v6`. Юнит перечитывается, только если его текст изменился.

Повтор с теми же правилами не вызывает `iptables-restore` и не возвращает FORWARD в ACCEPT. После этого шага старый SSH-порт снаружи закрыт.

```shell
sudo ./1-server-setup/15-secure-firewall.sh
sudo reboot
```

## 2. Установка ПО

### `2-install-software/20-install-oh-my-zsh.sh`

Ставит oh-my-zsh в домашний каталог того, кто запустил скрипт. Это не root-скрипт: `checkRoot` нет. Нужен `zsh` из скрипта 10. В батче шаг идёт от `TARGET_USER`.

Если каталог `~/.oh-my-zsh` уже есть, скрипт сразу заканчивается `[OK]`. Иначе качает установщик с `RUNZSH=no` и `CHSH=no`: оболочку не меняет и установщик не оставляет открытым zsh. Смена оболочки на zsh — скрипт 30.

```shell
./2-install-software/20-install-oh-my-zsh.sh
```

### `2-install-software/21-install-node.sh`

Ставит Node.js из NodeSource. Запуск от root. `VERSION` — мажор, по умолчанию 25, ведущая `v` снимается.

Если `node -v` уже этой мажорной версии, скрипт выходит. Иначе сначала проверяет, что `https://deb.nodesource.com/setup_<версия>.x` открывается, и только потом запускает его и `apt-get install nodejs`. Недоступный URL не оставляет полуустановленный репозиторий.

```shell
sudo VERSION=22 ./2-install-software/21-install-node.sh
```

### `2-install-software/22-install-docker.sh`

`2-install-software/22-install-docker.sh` — выбор дистрибутива, не установка. Запуск от root. Читает `ID` из `/etc/os-release`.

- `ubuntu` — выполняет `22-install-docker-ubuntu.sh`.
- `debian` — выполняет `22-install-docker-debian.sh`.
- другое значение — `[ERROR]`, ничего не ставит.

Оба файла установки делают одно и то же на своём репозитории Docker: если `docker compose version` уже работает, выходят до apt. Иначе ставят ключ, источник пакетов и `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`. Отдельной команды `docker-compose` с дефисом скрипт не требует.

```shell
sudo ./2-install-software/22-install-docker.sh
```

### `2-install-software/22-install-docker-ubuntu.sh`

Установка Docker на Ubuntu. Запуск от root. Обычно его вызывает `22-install-docker.sh`, напрямую тоже можно.

Если `docker compose version` уже выполняется, скрипт печатает версии и выходит до apt. Иначе ставит `ca-certificates` и `curl`, кладёт ключ Docker в `/etc/apt/keyrings/docker.asc`, добавляет источник `download.docker.com/linux/ubuntu` с кодовым именем из `/etc/os-release` и ставит `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`.

Повтор при уже рабочем `docker compose` пакеты не трогает.

```shell
sudo ./2-install-software/22-install-docker-ubuntu.sh
```

### `2-install-software/22-install-docker-debian.sh`

То же, что ubuntu-скрипт, для Debian: источник `download.docker.com/linux/debian` и кодовое имя Debian. Ранний выход тот же: рабочий `docker compose version` останавливает скрипт до apt.

```shell
sudo ./2-install-software/22-install-docker-debian.sh
```

### `2-install-software/23-docker-autoprune.sh`

Ежедневно удаляет неиспользуемые образы. Запуск от root после скрипта 22: без бинаря `docker` файл не создаётся.

Пишет `/etc/cron.daily/docker-image-prune` с командой `docker image prune -f` и делает его исполняемым. Если эта строка в файле уже есть, второй раз файл не трогает.

```shell
sudo ./2-install-software/23-docker-autoprune.sh
```

### `2-install-software/24-install-nginx-certbot.sh`

Ставит nginx и certbot и закрывает чужие домены заглушкой. Запуск от root. Страницы ошибок сюда не входят: их подключает только скрипт 43. Повторный запуск 24 переписывает `default.conf` своим шаблоном и снимет include, который успел добавить 43. После такого повтора 43 запускают снова.

1. Ставит `nginx`, `certbot`, `python3-certbot-nginx`, если какого-то пакета нет.
2. Удаляет `/etc/nginx/sites-enabled/default`.
3. Пишет `/etc/nginx/conf.d/default.conf` одним блоком `sst`: порт 80 отвечает редиректом на https, порт 443 — `default_server` с самоподписанным сертификатом, `ssl_protocols TLSv1.2 TLSv1.3` и `return 404`. Строка `listen 443 ssl http2` остаётся: nginx 1.18 не принимает `http2 on`. Код ответа заглушки остаётся 404.
4. Сертификат заглушки создаётся один раз: `/etc/nginx/ssl/default-reject.crt` и соседний ключ, CN `invalid`.
5. `nginx -t`. Не прошёл — файл возвращается из копии или удаляется, если его не было. Прошёл — reload только если файл изменился.
6. `certbot show_account` уже успешен — регистрация пропускается. Иначе нужен `CERTBOT_EMAIL`. В терминале скрипт его спросит. Без терминала и без переменной — ошибка до `certbot register`. Регистрация идёт с `--non-interactive --agree-tos`.
7. Если в `/etc/cron.daily/certbot-renew` ещё нет строк `certbot renew` и `nginx -s reload`, пишет этот cron.

```shell
sudo CERTBOT_EMAIL=admin@example.com ./2-install-software/24-install-nginx-certbot.sh
```

### `4-services/41-add-ssl-certificate.sh`

Выпускает сертификат одного домена и кладёт шаблон nginx. Запуск от root после скрипта 24 (nginx и certbot) и после скрипта 15 (снаружи открыты 80 и 443). Имя домена — `DOMAIN`. ### `4-services/42-manage-forward.sh`

Интерактив на машине-шлюзе: проброс SSH (tcp) и AWG (udp) на другой сервер. Запуск от root в терминале. В батч не входит. Без терминала скрипт сразу выходит.

Печатает два пути:

- `/etc/iptables/forward-rules.conf` — какие пробросы скрипт помнит;
- `/etc/iptables/rules.v4` — снимок всего iptables, его же пишет скрипт 15.

Меню из шести пунктов. Цифра 1–5 запускает пункт сразу. Стрелки и Enter выбирают подсвеченную строку. `0` и `q` выходят.

1. Список: конфиг, живой iptables и снимок. Колонка «после ребута» показывает, переживёт ли набор перезагрузку. Одного живого `ip_forward=1` мало: единица должна быть в sysctl-файле.
2. Добавить. Спрашивает локальные порты tcp/udp, локальный IP, порты и IP сервера. Та же шестёрка второй раз — `[ERROR]`, правила не дублируются. Форвард включается только вместе с DROP на FORWARD. Пока политика не DROP, sysctl-файл не пишется и правило не добавляется: сначала нужен скрипт 15. Если пересылка выключена, а политика уже DROP, пишется `/etc/sysctl.d/99-sst-ip-forward.conf` и применяется `sysctl --system`. В снимок `rules.v4` добавление не пишет.
3. Удалить. Пустой конфиг — предупреждение. Номер записи и слово `yes`. Снимает шесть правил и строку конфига. Снимок не меняет. Удалённый номер снова не выдаётся.
4. Сохранить. Слово `yes`. В `rules.v4` попадает весь текущий iptables, включая правила скрипта 15, не только форвард.
5. Загрузить. Файла нет — `[ERROR]`. Слово `yes` и предупреждение: несохранённые правила пропадут, SSH может оборваться, если в снимке другой порт или нет accept для текущего. `iptables-restore` подменяет весь набор. Конфиг форварда при загрузке не меняется.

```shell
sudo ./4-services/42-manage-forward.sh
```

### `4-services/43-nginx-error-pages.sh`

Подменяет тело выбранных кодов ошибок одной страницей. Запуск от root после скрипта 24: нужен бинарь nginx. В пресете `unattended-web` шаг стоит после 41.

Страница: `/var/www/nginx-errors/error.html`. Сниппет: `/etc/nginx/snippets/sst-errors.conf`. Коды 400, 401, 403, 404, 405, 408, 413, 414, 429, 500, 502, 503, 504 уходят в location `@sst_error` с тем же кодом (`error_page 404 =404 @sst_error`), не с 200. Include вставляется один раз, сразу после `server {`, в файлы `/etc/nginx/conf.d/*.conf` и `sites-enabled`. В блоке уже есть свой `error_page` — блок не меняется, пишется `[WARN]` с путём файла. `root`, `listen`, `server_name` и сертификат сервера скрипт не трогает.

### `4-services/44-remove-nginx-error-pages.sh`

Возвращает штатные ответы nginx. Запуск от root. В пресеты батча не входит. Пакеты не ставит и не удаляет.

Сначала проверяет, ставились ли страницы. Считается, что ставились, если выполняется любое: в сниппете есть `error_page` или `@sst_error`; существует `error.html`; в `conf.d` или `sites-enabled` есть include, и сниппет при этом не пустой. Пустой файл-заглушка без HTML и без этих директив — не установка.

Не ставились: ничего не правит, `nginx -t` не вызывает, `[OK]` «кастомные страницы не применены». Заглушку, `/etc/nginx/ssl/default-reject.crt` и чужие файлы в `snippets` не трогает.

Каталог `sites-available` сам не обходит: симлинк из `sites-enabled` правится один раз. Удаляет `error.html` и пустой каталог страниц, сниппет и пустой каталог `snippets`.

Бинарь nginx есть — `nginx -t`. Не прошёл: копии возвращаются, reload нет. Прошёл — reload. Бинаря нет, а файлы страниц есть: файлы удаляются по тем же правилам, reload не вызывается. Повтор после успешного снятия идёт веткой «не применено».

```shell
sudo ./4-services/44-remove-nginx-error-pages.sh
```
